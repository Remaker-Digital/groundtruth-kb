# Canonical terminology

Read a term through `gt authority resolve "<term>"` or `gt terms show <id>` and
inspect the current formal requirement with `gt spec show <id>`. Current native
domain records supply definitions and status; a copied glossary, generated
instruction or historical release report does not supply a second authority.

The authored usage guide and terminology configuration live at
`.harness-baseline-configuration/rules/canonical-terminology.md` and
`.harness-baseline-configuration/rules/canonical-terminology.toml`. Read focused
rules there on demand. They are not copied into each host's rules directory.
Shared skills live under `.agents/skills`; root `AGENTS.md` directs native
binding, current-state retrieval and task-scoped loading. See
[Harness projection](harness-projection.md).

## Terms that affect work

A program plans and sequences outcomes. A project is the execution authorization
and coherent commit unit. A work item has one execution-project parent. A claim
reserves delivery of one next artifact, not ownership of a work item or chain.

The exact supplied init establishes a context's immutable role; a vendor, host,
model or registration tag does not. Authorization is the owner's binary value
on the project row. Formal scope, review, current claims and executable tests
remain separate readiness requirements.

VERIFIED records independent review of exact work-product identities. The
complete project commit activates that authored work. Generated projections
are materialized operationally and excluded from the work-product commit.
Bridge messages provide dispatched instructions at receipt; later actions
re-query canonical state. Deliberations and session logs do not record owner
decisions as an alternate source of truth.

## Correct a definition or usage

Retrieve the exact current term and affected formal records. Apply an approved
semantic correction through the existing native writer, preserve formal history
by amendment or retirement, and read back the result. Reconcile affected source,
tests, authored rules/skills and documentation, then regenerate declared outputs.
Do not repair usage by editing a projected glossary or restoring a retired
SQLite/Markdown authority fallback.

Doctor and assertions inspect their current declared sources. Their success is
bounded to those checks; it does not establish formal closure or native host
loading. Report any missing or conflicting requirement through current work
intake and keep its correction within the selected execution scope.
