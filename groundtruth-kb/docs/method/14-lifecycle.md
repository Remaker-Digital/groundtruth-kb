# 14. From current intent to complete project commitment

A program plans and sequences projects. A project groups the interdependent
changes that complete together and is the authorization and commit unit. A work
item defines one testable artifact/control-surface result or observable action
and has exactly one project parent. Labels and prose are not membership.

Apply adequately defined owner requirements and choices directly to the current
formal or domain source. Discussion can explain reasoning but is not an approval
archive or mandatory stage. Project authorization is the owner's binary project
field used for work ordering; independent review, executable evidence, claims
and effect boundaries remain separate requirements.

## The ordinary implementation sequence

| Stage | Result and condition |
| --- | --- |
| Define and plan | Current formal intent, complete project outcome, single work-item membership, executable test and test-plan instructions, dependencies. |
| Propose | Prime Builder checks current parent authorization before NEW and authors the complete specification-linked proposal with target paths and verification plan. |
| Review proposal | A distinct eligible Loyal Opposition context authors GO or NO-GO. A revised proposal uses REVISED. GO accepts implementation intent; it does not verify implementation. |
| Implement and report | The selected Prime Builder context claims its exact next artifact and applies the accepted scope under current native effect checks, then delivers READY. |
| Verify | Independent Loyal Opposition tests the actual result against current formal intent and the proposal, then authors VERIFIED or NOT-READY. A corrected report uses READY. |
| Commit the complete project | Once every member is VERIFIED, the native CLI instructs the verifying Loyal Opposition context to commit the complete independently reviewed work through normal hooks. |

Each response is assigned to a role and claimed by its receiving context. A claim
reserves one next artifact, never the work item or thread. A successor obtains
its own claim; the original author need not return. The bridge message is
authoritative at receipt and has no continuing authority. Later actions re-query
canonical state. Harnesses coordinate only through the CLI and bridge.

## Verification and terminality

VERIFIED records the reviewed Git mode and object ID for each concrete artifact,
including explicit absence for deletions. It is not proof of commitment. The
single project commit includes every retired work-item citation and the complete
verified work product. Bridge payloads and generated projections are excluded.
The exact authored baseline/projector sources must be able to produce their
derivations; operational refresh materializes generated output.

A successful project commit activates the authored work and establishes terminal
work. Canonical state mirrors the Git fact. Publication supplies durability and
follows its applicable direction; it is not implicitly performed by session wrap.
Committed work is not reopened. Reversal or removal is new forward work.

## Change and failure before commitment

Changed verified bytes require fresh independent verification. A failed commit
records its typed canonical finalization failure and returns affected work for
fresh independent verification without a dispatcher-authored verdict.

Material formal-intent change after VERIFIED, before commitment, requires a fresh
proposal, review, implementation and verification attempt on the same uncommitted
work item. Use the native restart route, preserve its identity, parent and bytes,
and inherit no GO or effect authority from the abandoned attempt. Do not turn
verification of earlier intent into implementation permission for changed work.

Complete behavior includes rejected inputs, concurrency, interruption, recovery,
fresh contexts and independent successors. A narrow test pass or inventory is
coverage evidence only. Missing capability and incomplete review remain open.
