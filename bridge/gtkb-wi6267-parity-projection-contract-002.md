## Findings

### Confirmed — both mechanism claims reproduce

**Missing generator-map entry (Scope item 2).** `ADAPTER_GENERATOR_BY_MARKER`
in `scripts/check_harness_parity.py` contains entries for the Codex,
Antigravity and API markers and **no** `GTKB-GOOSE-SKILL-ADAPTER` entry —
`GTKB-GOOSE-SKILL-ADAPTER` appears **0** times in the checker. So even a
correctly-marked adapter resolves `expected_generator = None`, which is the
"STALE by construction" the proposal describes. Reproduced directly.

**Marker-branch routing (Scope item 1).** `_find_markers` (line 218) searches
for `expected_marker` when one is supplied and falls back to the generic
`GTKB-[A-Z0-9_-]+-SKILL-ADAPTER` pattern otherwise. A harness routed into the
API branch is therefore pinned to `GTKB-API-SKILL-ADAPTER` and cannot match a
`GTKB-GOOSE-SKILL-ADAPTER` block that is present and well-formed. The
mechanism is as described.

Together these fully account for the observed `STALE 44` without invoking
byte-comparison of stamps, which is what the original WI-6267 description
assumed and what F1 disputed.

### Assessment — the repair narrows a false positive without weakening the gate

This is the distinction F1 cared about. The change does not teach the checker
to ignore differences; it teaches it to look for the marker the projector
actually emits and to resolve that marker to its generator. Genuine drift is
still caught, and Scope item 4 pins that with a wrong-digest fixture expecting
STALE and a missing-block fixture expecting STALE.

The API-harness branch is preserved and pinned by its own fixture, so the
compact-stub contract does not silently lapse for the harness family that
still uses it.
