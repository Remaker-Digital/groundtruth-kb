## Corrected Mechanism — Four Causes, All Reproduced

Measured this session against `.goose/skills/gtkb-bridge/SKILL.md` and
`scripts/check_harness_parity.py`.

**M1 — marker-branch routing (was Scope 1; confirmed).** `goose` declares both
`projection_engine` and `skill_adapter_manifest`, so `manifest_adapters`
membership routes it into the API branch at line 668-670 and pins
`expected_marker = "GTKB-API-SKILL-ADAPTER"`. Live evidence: all 44 STALE notes
read `... for GTKB-API-SKILL-ADAPTER`.

**M2 — missing generator-map entry (was Scope 2; confirmed).**
`ADAPTER_GENERATOR_BY_MARKER` (lines 160-164) holds exactly three keys — CODEX,
ANTIGRAVITY, API. `GTKB-GOOSE-SKILL-ADAPTER` resolves `expected_generator =
None`.

**M3 — the marker parser cannot read the projector's grammar (NEW; not in the
approved scope).** `_find_markers` (line 218) locates the opening marker with
`<!--\s*(MARKER)` and the closing marker with `MARKER\s*-->`. The projection
engine emits the block as
`<!--\nMARKER-BEGIN\n...\nMARKER-END\n-->`
(`project_harness.adapter_metadata_block`, lines 121-138). The closing form is
`MARKER-END\n-->`, which `MARKER\s*-->` does not match. Probe result, with the
**correct** marker supplied:

```text
--- expected_marker='GTKB-GOOSE-SKILL-ADAPTER'
  _find_markers -> None
  _adapter_metadata keys -> []
  Generated by -> None
```

So M1 and M2 together are **not sufficient**: even after routing to the right
marker and mapping it to a generator, `_adapter_metadata` returns `{}` and the
capability still reports STALE on the `Generated by` check at line 678.

**M4 — no expected-content renderer for a projected harness (NEW; not in the
approved scope).** `_render_expected_adapter` (lines 301-312) registers
renderers for the CODEX, ANTIGRAVITY and API markers and returns `None`
otherwise. Probe result: `_render_expected_adapter(..., expected_marker=
"GTKB-GOOSE-SKILL-ADAPTER") -> None`, which reaches line 725-730 and reports
STALE `No semantic adapter renderer is registered`.

M3 and M4 are each independently sufficient to keep every goose adapter STALE
after the approved fix lands. That is why this revision is filed.

## Corrected Scope

1. **Route by projection contract (M1).** A harness whose registry block
   declares `projection_engine` resolves `expected_marker =
   GTKB-<HARNESS>-SKILL-ADAPTER` regardless of `skill_adapter_manifest`.
   Enumerated this session — `goose` is the **only** harness declaring
   `projection_engine`; `cursor`, `ollama`, `openrouter` and
   `alibaba-cloud-studio` declare `skill_adapter_manifest` alone and keep the
   API branch unchanged. This closes the `-002` "not verified" note.

2. **Resolve the generator from the registry declaration (M2).** When a harness
   declares `projection_engine`, `expected_generator` is that declared value;
   the static `ADAPTER_GENERATOR_BY_MARKER` remains the source for the three
   stub-contract markers. Preferred over adding a hard-coded goose row because
   each Phase-D cutover would otherwise re-break parity until someone
   remembered to edit the map — the same defect class this thread is repairing.

3. **Teach the marker parser the BEGIN/END grammar (M3).** `_find_markers`
   additionally recognises `MARKER-BEGIN` / `MARKER-END`. The existing
   `MARKER` / `MARKER -->` form is preserved and pinned by fixture, so
   CODEX/ANTIGRAVITY/API parsing is unchanged.

4. **Delegate expected content to the projection engine (M4).** For a
   `projection_engine` harness, `_render_expected_adapter` returns
   `project_harness.build_plan(harness).writes[surface]`. Measured: the plan
   yields 127 writes with zero gaps and is **byte-identical** to every managed
   on-disk path, so this is a stricter oracle than the stub comparison, not a
   weaker one. `build_plan` is invoked lazily on first use and memoised per
   harness per run; measured cost 2.9 s (33 `ruff format` subprocesses over
   `.py` writes), paid once and only when a projected harness is selected.
