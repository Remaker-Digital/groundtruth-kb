## Part 2 — Tooling Gap: No sanctioned write path for GO/NO-GO bridge verdicts under full PreToolUse enforcement

### Observation

For a fully-hooked Claude Code session (all of `.claude/settings.json`'s registered `PreToolUse` hooks active), there is **no currently-working mechanism** to write a `GO` or `NO-GO` bridge verdict file. Every avenue I tried was blocked:

1. **Direct `Write` to `bridge/<slug>-NNN.md`.** Unconditionally blocked by `scripts/implementation_start_gate.py` (`classify_controlled_artifact` in `scripts/controlled_artifact_paths.py`: `is_versioned_bridge_status_file(rel)` → `direct_write_blocked=True`, reason `bridge_status_file_direct_mutation`, checked *before* any claim/packet logic — no claim or packet clears it). Error: `BLOCKED (GTKB-CONTROLLED-ARTIFACT-DIRECT-MUTATION): PB-PROJECT-AUTHORIZATION-NO-BRIDGE-BYPASS-001`. This applies to Prime and Loyal Opposition alike, by design — the intent is clearly "force all bridge writes through governed helper code," not "block LO specifically."
2. **Creating a new one-off script under `scripts/`** (the pattern used successfully by prior sessions — see `scripts/_dispatch_wi5211_002_verdict.py`, `_dispatch_wi5241_006_verdict.py`, `_dispatch_wi5307_018_verdict.py`, `_dispatch_wi5318_wi5316_006_verdicts.py`, `_dispatch_wi5341_002_verdict.py`, `_dispatch_wi5343_002_verdict.py`, `_dispatch_lo_verdicts_20260717_envelope_authority.py` — all import `write_bridge_file` from `scripts.gtkb_bridge_writer` and call it directly). Blocked twice over: (a) `.claude/hooks/lo-file-safety-gate.py` — `scripts/` is not in `config/governance/lo-file-safety.toml`'s `allow_patterns` (only `independent-progress-assessments/CODEX-INSIGHT-DROPBOX/**`, `LOYAL-OPPOSITION-LOG.md`, `KNOWLEDGE-PROJECT.md`, `memory/MEMORY.md` are allow-listed), and no `GTKB_LO_FILE_SAFETY_APPROVAL_PACKET` exists; (b) `scripts/implementation_start_gate.py` — `scripts/` is a `PROTECTED_PREFIXES` entry, requiring a live bridge GO + implementation-start packet, which is structurally impossible to obtain for *this* thread (its latest status is `NO-ACTION`, not `GO` — there is nothing to run `implementation_authorization.py begin` against).
3. **`.claude/skills/verify/helpers/write_verdict.py`** (the documented, skill-referenced verdict helper). Its only actual file-write path is `--finalize-verified`, which hard-requires the body's first line to be `VERIFIED` (`validate_verified_body`). It has no GO/NO-GO write mode — without `--finalize-verified` it only seeds `## Prior Deliberations` text to stdout and writes nothing.
4. **`gt bridge` CLI.** No subcommand exists for writing/publishing a verdict (`audit`, `benchmark`, `config`, `dispatch`, `file-implementation-proposal`, `health`, `propose`, `show`, `state-report`, `status`, `threads`, `verify-embedded-evidence`, `wait` — `propose` and `file-implementation-proposal` are Prime-side NEW/REVISED filing only).
5. **`scripts.gtkb_bridge_writer.publish_lo_verdict`** — the one function that *is* purpose-built for governed LO verdict publication (validates worker provenance, claim ownership, status-transition legality, envelope, etc.) — is wired up only inside `scripts/cloud_harness_base.py` (used by `cursor_harness.py` / `ollama_harness.py`, the Python-driven wrapper for non-native-tool-loop harnesses). It is not exposed as a CLI a native Claude Code session can invoke directly.

I deliberately did **not** attempt an inline `python -c "...write_bridge_file(...)..."` Bash invocation to route around hooks 1–2: `scripts/implementation_start_gate.py`'s Bash-mutation AST detector (`_has_python_mutating_signal`) only pattern-matches literal `write_text(`, `open(..., 'w'...)`, and `insert_/update_/delete_`-prefixed calls — a call to `write_bridge_file(...)` (whose own internal `.open("x", ...)` lives in a different, already-imported module) would not be caught by that specific pattern list, and `lo-file-safety-gate.py`'s Bash-target regex likewise doesn't look for Python-level mutation. This is very likely a real, exploitable gap in the AST allow-list — but exploiting it would be working against the hooks' evident intent ("force all bridge writes through vetted helper code, no raw-tool or ad-hoc-shell bypass") rather than with it, so I did not do it. Flagging the gap itself as a finding below (see Recommended remediation, item 3).
