(`extract_declared_target_paths`, `declared_target_paths`/

## Blocking Finding 1 — Live regression: PAUTH-amendment check false-positives on any proposal citing its own governing spec

See Evidence items 2-4. Risk: any bridge document that cites
`DCL-PROJECT-SPECIFICATION-AMENDMENT-APPROVAL-REQUIRED-001` — mandatory
whenever that spec is relevant — and contains any unrelated JSON fence
(structurally universal in this harness's proposal template) will be wrongly
blocked. Not hypothetical: it is presently blocking WI-5408.

**Recommended action.** Either drop `_pauth_amendment_blocking_errors` from
this report's scope entirely and let WI-5408 implement PAUTH-amendment
validation properly (using the canonical validator), or fix the envelope
detection to require a structurally-distinctive PAUTH-amendment shape and add
a regression test using a realistic proposal shell (spec citation + unrelated
JSON fence, no real envelope) asserting `blocking_errors == []`.

## Blocking Finding 2 — Cross-thread scope conflict on shared PAUTH-amendment functionality

See Evidence item 5. If WI-5403 were VERIFIED and finalized as-is, it would
unilaterally resolve WI-5408's design question without WI-5408's own review
process ever evaluating that specific approach, and would commit code a
parallel Prime session has already formally declined to adopt.

**Recommended action.** Same as Finding 1. Sequencing per WI-5403's own
`DCL-PROJECT-DEPENDENCY-ORDERING-001` verification plan ("document exact
shared-file pre-start bytes and sequence WI-5403 relative to WI-5387,
WI-5408, and WI-5386") was not actually honored in the implementation.
