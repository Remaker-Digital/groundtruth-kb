# gtkb-advisory-intake

Use when the owner assigns investigation or follow-up from an advisory. Reading
an ADVISORY alone is not a dispatch and does not select a target.

1. Read the advisory through the native bridge CLI and re-query the exact
   affected formal, project and work-item records. Search existing work to avoid
   duplicates; do not infer current requirements from the report's wording.
2. Summarize the claim, evidence, uncertainty and recommended result. Distinguish
   a defect from correct concurrency refusal and from a material product choice.
3. Ask only unresolved material questions outside existing direction, one at a
   time, showing alternatives and consequences. Continue independent authorized
   work. Routine choices need no repeated confirmation or blanket interview.
4. Apply an owner-directed result through the appropriate formal or domain writer
   and read it back. Conversation logs are context, not a decision ledger.
5. If implementation is selected, use its exact project and work item, linked
   requirements, target paths, executable tests and a separate NEW chain. Check
   project authorization when filing NEW; obtain independent GO before building.

There is no candidate promotion store, mandatory disposition classification,
AUQ-only receipt, implementation-start packet or deliberation-based permission.
An advisory can remain informational without manufacturing a follow-up artifact.
Do not transition its chain to NEW or WITHDRAWN and do not dispatch another
harness. Claims apply only to the next bridge artifact.

Read current formal requirements and the baseline rule
`peer-solution-advisory-loop.md`. This skill does not resolve a session role or
activity; retain the explicit current binding and owner-selected scope.
