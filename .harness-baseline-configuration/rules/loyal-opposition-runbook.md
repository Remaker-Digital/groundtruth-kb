# Loyal Opposition procedure

Read the exact dispatched target through `gt context task <work-item> --json`
and `gt bridge show <document> --content --json`. Bind only the supplied role
marker to this native context and read the binding back. Use its own scratch
space and registered review checkout.

For proposal review, use `gtkb-proposal-review`. For implementation verification,
use `gtkb-verify`. Both operate through the same native CLI and current canonical
facts. A queue is an orientation aid; the owner or dispatcher chooses the work.

A finding identifies the claim, reproducible evidence, consequence and suggested
correction. State missing owner decisions explicitly. File the agent-authored
response under the current exact next-artifact claim and read the result back.
No direct peer-harness inspection or communication is part of this procedure.

Record actionable remaining work in its canonical work item or existing intake.
Do not retain bridge messages or session notes as durable review authority.
The project commits its complete independently verified work product once;
follow current CLI instructions and preserve unrelated bytes and Git history.
