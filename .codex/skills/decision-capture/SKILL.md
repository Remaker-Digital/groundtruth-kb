This skill implements the Deliberation Archive (DA) tier of ADR-0001: Three-Tier Memory Architecture.

# /gtkb-decision-capture

## What this skill does

Records an owner decision as an append-only entry in the Deliberation
Archive via `KnowledgeDB.insert_deliberation()`. Fixed metadata:
`source_type="owner_conversation"`, `outcome="owner_decision"`. Never
mutates specs, work items, or other artifacts. Enforces DELIB-ID
collision checks so repeated IDs raise explicitly rather than
silently version-bumping an unrelated record.

## When to invoke

Use this skill when:

- Owner makes a scope/policy/design decision during a session
- Owner selects one option over considered alternatives
- Owner grants explicit approval that should be durable across sessions

Do NOT use for:

- Routine protocol acknowledgments (bridge GO/NO-GO acks)
- Code review feedback (use Loyal Opposition reports instead)
- Session-scoped reminders (use `MEMORY.md`)

## How it works

Invokes `helpers/record_decision.py` with the owner-supplied:

- DELIB-ID (fresh, caller-generated; collision raises
  `DeliberationIDCollisionError`)
- `title` and `summary` strings for list / detail views
- `content` capturing the decision, options considered, and rationale
- Optional `spec_id`, `work_item_id`, `participants`, `session_id`
  links for traceability

The helper calls `KnowledgeDB.insert_deliberation()` with the fixed
metadata and returns the persisted row as a `dict[str, Any]`. Raises
`DeliberationInsertFailed` if the underlying insert unexpectedly
returns `None`.

Redaction of credential patterns in the `content` body is performed
inside `insert_deliberation()`; the helper does not duplicate that
pass.

## Composite owner-decision workflow

Some owner exchanges produce several AskUserQuestion (AUQ) answers that
belong to **one coherent decision** rather than several independent ones.
The S363 v1.0 release-strategy exchange is the canonical example: eight AUQ
answers were composed into the single record `DELIB-2234`, and a smaller
confirmation AUQ became `DELIB-2238`. This section defines when and how to
capture those as one composite Deliberation Archive record.

### When to consolidate vs. split

**Consolidate** several AUQ answers into one composite record when:

- The answers resolve one owner deliberation on a single topic or session
  (e.g., the numbered open questions of one strategy document).
- The answers are interdependent — later answers only make sense given the
  earlier ones, or the implications cut across the whole set.
- A future session would want to read them together to reconstruct the
  decision, not one at a time.

**Split** into separate atomic records (the baseline `record_decision`
path) when:

- The answers resolve unrelated topics that happen to arrive in the same
  turn.
- Each answer stands on its own and would be searched or cited
  independently.
- Consolidating would bury one decision inside an unrelated one.

When in doubt, prefer the atomic path — a composite record is only worth
its weight when the answers genuinely form one decision.

### Composite content shape

A composite record uses `helpers/record_decision.py:compose_composite_content()`
to build the `content` body, then passes that body to the same
`record_decision()` write path. The composed body carries four fixed
sections:

- `## Decisions` — a markdown table, one row per AUQ answer, with a
  **source-ref** column, the decision, and its rationale anchor.
- `## Composed Implications` — bullets that hold across the whole set,
  capturing cross-answer consequences a single-answer record could not.
- `## Linked Artifacts` — the specs, ADRs/DCLs, bridge threads, memory
  snapshots, and sibling deliberations the decision touches, named by their
  canonical source-ref (e.g., `bridge/<slug>-NNN.md`, `DELIB-NNNN`,
  `ADR-...`).
- `## First Concrete Actions Authorized` — the numbered next steps the
  composite decision authorizes.

### source-ref and AUQ-id naming

Each decision row records where the answer came from so the composite stays
traceable:

- For answers derived from an AskUserQuestion pop-up, use the **AUQ-id**
  form `AUQ-<n>` (or the owner-supplied question label) as the source-ref.
- For answers that resolve a numbered section of a predecessor deliberation
  document, use the section anchor form (e.g., `§9.1`) as the source-ref,
  matching the `DELIB-2234` exemplar.

Keep the naming stable within one composite record so the Decisions table
reads as one coherent set.

### Fixed metadata and atomic path are preserved

The composite workflow only changes how the `content` body is composed. It
does **not** change the write path: composite records are still inserted via
`record_decision()` with the same fixed `source_type="owner_conversation"`,
`outcome="owner_decision"`, `changed_by`, and `change_reason`, and the same
DELIB-ID collision guard. The atomic single-decision path remains available
unchanged — callers with one owner decision do not supply composite fields
and call `record_decision()` directly.
