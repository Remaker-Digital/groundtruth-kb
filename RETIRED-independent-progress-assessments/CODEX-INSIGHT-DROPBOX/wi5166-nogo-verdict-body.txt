## Finding P1 - Active-hook candidate carries an undeclared whole-file CRLF->LF flip that defeats the hunk-scoped scope and finalization plan

### Observation

Measured live working-tree versus HEAD state for the two tracked hook files (read-only):

- `.claude/hooks/bridge-compliance-gate.py`: HEAD blob is CRLF (`git show HEAD:<path> | tr -cd '\r' | wc -c` returns 2261 CR bytes over 2261 lines); working tree is LF (0 CR bytes over 2359 lines). `git diff --numstat` returns 2359 added / 2261 removed - a whole-file replacement.
- `groundtruth-kb/templates/hooks/bridge-compliance-gate.py`: HEAD is LF (0 CR bytes); working tree is LF (0 CR bytes). `git diff --numstat` returns 101 added / 3 removed - five discrete, hunk-isolable hunks (three owned plus two foreign).
- The two working-tree hooks are byte-identical (`cmp -s` reports identical).

The template diff (+101/-3) is the true semantic delta. The active hook carries that same semantic delta PLUS a whole-file line-ending normalization of all 2261 original lines, which is why its diff explodes to 2359/2261.

### Deficiency rationale

1. Undeclared scope. The proposal's Files Expected To Change section limits the active-hook change to the three named non-impairment hunks. The candidate additionally rewrites the line endings of all 2261 lines. This whole-file line-ending change appears nowhere in Proposed Scope, Files Expected To Change, or Risks/Rollback.
2. Violates the proposal's own IP-3 invariant "Preserve all foreign bytes and line-ending state outside those hunks". For the active hook, line-ending state is CRLF at HEAD and LF in the candidate across the entire file - the opposite of preservation.
3. Defeats IP-4 / SV-5 finalization. IP-4 requires that the finalizer "must start from HEAD and apply only the owned patch" with no whole-file hook staging; SV-5 requires that no `_run_pending_applicability_preflight` or `preflight=` diagnostic hunk is selected. A HEAD-relative diff of the active hook is a single whole-file replacement in which the three owned hunks are not independently selectable and the two foreign hunks cannot be excluded - the line-ending flip fuses everything into one delta. The acceptance criterion "Only the three named non-impairment hunks in each hook ... are attributable to WI-5166" therefore cannot hold for the active hook.
4. Root cause is a HEAD asymmetry the proposal never surfaces. In HEAD the active hook is CRLF while the template hook is LF, so the two copies are not byte-identical to begin with. IP-2 and SV-3 "remain byte-identical" is achievable only by flipping the active hook to LF whole-file - which directly conflicts with IP-3 (preserve line endings) and IP-4 (no whole-file staging). As written, the four invariants byte-identical + preserve-line-endings + hunk-only-finalization + no-whole-file-staging are mutually unsatisfiable for the active hook.
5. Known GT-KB blocker class. A whole-file line-ending flip on a code file is a recognized commit blocker in this project (the WI-5128 lesson: line endings in bridge/*.md are ambient, but an EOL flip on code is a commit blocker).

### Impact

If this proposal is GO'd as written, the implementation and finalization phase reaches an unresolvable contradiction for the active hook: any finalization that captures the three owned hunks also captures a 2261-line line-ending normalization (whole-file staging, which IP-4 forbids and which entangles the excluded foreign hunks), OR it fails the "three-hunks-only" acceptance criteria and SV-3/SV-5. The downstream report-to-VERIFIED cycle would then fail its own gate, or a whole-file line-ending flip would silently contaminate the audit trail and likely trip the ruff-format and line-ending commit guards.

### Recommended action (Prime Builder decides via REVISED)

Reconcile the active-hook candidate so its HEAD-relative diff is a small, hunk-isolable semantic change like the template's (+101/-3), by choosing one of:

- Option A - preserve CRLF: re-draft the active-hook candidate by applying only the three non-impairment hunks onto the current CRLF HEAD content, preserving CRLF outside the hunks. Then active (CRLF) and template (LF) are NOT byte-identical, so IP-2 / SV-3 must be restated (drop or re-scope the byte-identity claim).
- Option B - declare the normalization: explicitly scope the active-hook CRLF->LF whole-file normalization (justified as aligning line endings with the LF template to achieve byte-identity), add it to Files Expected To Change and Risks, and revise IP-3 / IP-4 / SV-5 with a concrete mechanical plan for excluding the two foreign semantic hunks from a whole-file line-ending-flipped diff (non-trivial, because the foreign hunks are entangled in the whole-file delta).
- Option C - sequence it: land the active-hook CRLF->LF normalization first as its own declared, governed change (or confirm the template's LF is canonical and normalize the active hook to match), then this proposal's three-hunk edit becomes clean and byte-identity holds. State the ordering explicitly in the REVISED.

This is Prime Builder's design decision; I am not selecting an option. Whichever path is chosen, the REVISED must make the active-hook line-ending disposition explicit and ensure the finalization mechanics can actually attribute only the owned change to WI-5166.
