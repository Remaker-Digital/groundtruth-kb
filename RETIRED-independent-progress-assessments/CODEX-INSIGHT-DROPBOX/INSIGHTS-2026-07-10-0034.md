The `-004` VERIFIED verdict (line 76, "Positive Confirmations") asserts:

### Deficiency rationale

- **Governance / audit accuracy:** an undisclosed ~1,500-line EOL flip committed
  under a `fix:` label is the scope-hidden-commit class flagged by the S333 audit
  (FINDING-P0-001). The implementation report (`-003`) and the VERIFIED verdict
  (`-004`) both describe an 8-line change; the commit is a whole-file rewrite of
  four files. A VERIFIED verdict should not embed a factual no-churn claim that
  the very commit it finalizes contradicts.
- **CI hygiene:** CRLF was introduced into a workflow executed on `ubuntu-latest`.
  GitHub Actions' YAML parser normalizes block-scalar line breaks, so the `run: |`
  shell blocks are *likely* tolerated and CI is *probably* not broken — but this
  is unauthorized EOL drift on an LF-canonical file, and it is the opposite of the
  reliability-improvement intent of the WI.
- **Recurrence:** this is at least the THIRD instance of "a bridge finalize landed
  a CRLF flip":
  - WI-5090: "Renormalize file-bridge-protocol.md + canonical-terminology.md to LF
    (WI-5081 finalize landed CRLF flip)".
  - WI-4722: "Re-do Codex adapter generator CRLF-fix edits LF-clean (worker edits
    CRLF-contaminated, fail `git diff --check`)".
  - WI-5102 (this): `a5c2dde0` finalize landed CRLF flip on the CI workflow + web
    tests.

### Root cause (probable)

Multi-session EOL race. The dispatcher and interactive sessions had several
harnesses touching these four files concurrently with differing line endings.
The peer measured a transiently LF-clean working tree (`git diff --numstat` vs
pre-commit HEAD = 8 lines) and concluded "LF baseline preserved," but by the time
the finalize helper ran `git add`, the working-tree bytes were CRLF (autocrlf
off, no `.gitattributes` normalization), so the commit stored CRLF. The verdict's
no-churn measurement and the commit's actual bytes were taken against different
transient worktree states.

## Proposed solution / enhancement (for Prime Builder — captured as backlog)

1. **Immediate (P2):** renormalize the four `a5c2dde0` target files to LF in a
   follow-up commit so the canonical stored blobs are LF (matching the pre-flip
   baseline and the repo LF norm). Verify each with
   `git cat-file blob HEAD:<path> | od -c` (expect `\n`, not `\r\n`) and
   `git show <fix-commit> --numstat` (expect ~8-line stat).
2. **Root-cause prevention (recommended, higher leverage):** extend the root
   `.gitattributes` to pin the recurring-offender paths to `text eol=lf` — at
   minimum `.github/workflows/**` and `groundtruth-kb/tests/**` (consider `*.yml`
   and `*.py` broadly). This makes `git add` normalize CRLF worktree bytes back to
   LF at stage time, which would have prevented WI-5081/WI-5090, WI-4722, and this
   WI-5102 instance regardless of the multi-session race.
3. **Process note (no separate WI):** the VERIFIED finalization path should treat
   a whole-file numstat on a nominally small change as a finalization smell — a
   pre-commit `git diff --stat` vs `--ignore-cr-at-eol` delta check before
   finalizing would catch this class deterministically.

### Option rationale

`.gitattributes eol=lf` is preferred over "ask every session to be careful about
EOL" because the failure is a salience/race problem, not a knowledge problem —
three independent finalizations already tripped it. A mechanical stage-time
normalization removes the race entirely for the covered paths. Enabling
`core.autocrlf=input` globally was rejected as the primary fix: it is a per-clone
setting (not enforced by the repo), so it does not travel with the repository the
way `.gitattributes` does.
