## The peer GO's premise is factually incorrect

The GO summary approves "adding support for `plan_incomplete` completion guards
to prevent premature automatic project retirement." That machinery is **not new
work** — it already exists, is governed by a current spec, and shipped a month
ago.

### Evidence

1. **Spec is already at v6 and already defines the mechanism.**
   `GOV-PROJECT-VERIFIED-COMPLETION-RETIREMENT-001` (version 6) already defines:
   - the `plan_incomplete` completion guard that blocks retirement;
   - a "premature-retirement safeguard" that names "the WI-3481
     incrementally-materialized-multi-slice risk" — the exact trap WI-4876 cites;
   - the keep-open caller election, surfaced as `retire_project: bool` and the
     `--keep-project-open` flag on `gt projects complete-authorization`.

2. **Code already implements it.**
   `groundtruth-kb/src/groundtruth_kb/project/lifecycle.py` defines
   `_COMPLETION_GUARD_RELATIONSHIP = "plan_incomplete"`,
   `_COMPLETION_GUARD_ARTIFACT_TYPES = ("completion_guard", "bridge_thread")`,
   `_project_completion_guard_refs`, `_completion_guards_by_project`, and
   `_project_keep_open_elected`. `complete_project_authorization` raises on any
   active guard; `auto_complete_ready_authorizations` skips guarded projects;
   `gt projects complete-authorization --keep-project-open` exists in `cli.py`.

3. **It shipped VERIFIED via a prior thread.**
   Commit `df274b81` (2026-06-07) "fix(project): guard incomplete completion
   plans", bridge thread `gtkb-project-completion-plan-incomplete-guard`
   (001–004), WI-3481 — touching the same files this proposal re-lists
   (`lifecycle.py`, `test_project_artifacts.py`, `test_project_completion_surface.py`,
   `test_project_verified_completion_scanner.py`,
   `project_verified_completion_scanner.py`). The proposal cites none of it.

## The P0 concern the GO did not surface

The proposal's Scope Changes say "Treat active `plan_incomplete` links whose
`artifact_type` is `completion_guard` as keep-open guards, **not completion
blockers**" and add auto-supersession. This:

- **Reverses a VERIFIED regression test.**
  `groundtruth-kb/tests/test_project_artifacts.py::test_auto_complete_plan_incomplete_guard_suppresses_completion`
  seeds a `completion_guard`-type guard and asserts
  `auto_complete_ready_authorizations(...) == []` with the authorization and
  project both staying `active`. The proposed design makes that test fail. The
  proposal never names the test or the reversal.
- **Contradicts spec v6**, which states "as long as ... a `plan_incomplete` guard
  is active, the project cannot be completed or retired" — while the proposal
  lists "Formal specification mutation" as out of scope.

## Recommended handling (for Prime and the eventual verifier)

1. **The genuine gap is narrow and spec-aligned:** `gt projects authorize` has no
   `--plan-incomplete` option and `authorize_project` creates no guard link, so
   there is no first-class *creation* path for a `completion_guard`-type guard at
   authorize time. That gap can be closed **without** reversing v6: an
   authorize-time guard already yields WI-4876's acceptance under existing
   semantics (guard suppresses interim auto-completion AND retirement; project
   stays active until Prime removes/supersedes the guard).
2. **If the owner wants the two-tier "completion_guard non-blocking +
   auto-supersede" model**, that is a substantive owner design decision requiring
   a v7 amendment to `GOV-PROJECT-VERIFIED-COMPLETION-RETIREMENT-001` and owner
   AskUserQuestion approval — it cannot be settled by a headless dispatch and
   should not be implemented silently under a "no spec mutation" scope.
3. **At post-implementation verification, the verifier MUST check** whether the
   implementation (a) alters/deletes
   `test_auto_complete_plan_incomplete_guard_suppresses_completion`, (b) diverges
   from spec v6 guard semantics, or (c) duplicates the shipped WI-3481 machinery.
   If any is true without an owner-approved v7 amendment, issue NO-GO.
