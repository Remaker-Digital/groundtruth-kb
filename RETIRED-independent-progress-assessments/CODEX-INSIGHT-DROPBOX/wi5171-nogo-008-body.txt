### F1 [P1] `cli_backlog_add_work_item.py` carries a whole-file LF to CRLF flip (scoped-commit blocker)

- Claim: finalizing `-007` as-is would commit a whole-file EOL flip on an authorized code file, violating the scoped-commit invariant and regressing the file's canonical line endings.
- Evidence (reproducible read-only commands, all run by this reviewer):
  - `git ls-files --eol -- groundtruth-kb/src/groundtruth_kb/cli_backlog_add_work_item.py` reports `i/lf  w/crlf` (index blob LF, working tree CRLF).
  - `git diff --stat` shows the file at 572 changed lines; `git diff --ignore-cr-at-eol --stat` collapses the same file to 12 — so roughly 274 of the 286 changed lines are pure end-of-line churn, not content.
  - `.gitattributes` covers `*.json`, `*.toml`, and specific skill/config directories only; it does NOT cover `.py` under `scripts/`, `groundtruth-kb/src/`, or `platform_tests/`. `git check-attr text eol` returns `unspecified` for the file, and `git config core.autocrlf` is unset. Therefore `git add` stages the CRLF bytes verbatim — the flip WILL be committed, not normalized away.
- Impact: the resulting VERIFIED commit would (a) bundle roughly 274 lines of unrelated EOL churn into a scoped WI-5171 commit, contradicting the bridge protocol scoped-commit invariant; and (b) flip this code file's canonical endings from LF to CRLF, which pollutes diff/blame and works against the active repo EOL-normalization program (`WI-5114`, `WI-5117`, `WI-5128`).
- Not droppable: the roughly 12 real content lines are load-bearing WI-5171 (they thread `project_root` into `resolve_changed_by` and pass the resolved `changed_by` through `_add_backlog_item`), so the file cannot simply be excluded from the finalization commit. It must be renormalized to LF so its diff collapses to those content lines.
- Why a headless reviewer cannot self-resolve it: renormalizing the file is a source-tree edit, which is outside Loyal Opposition write authority and cannot be owner-approved in an auto-dispatched worker. A hunk-scoped finalization does not help either — the working copy's content lines are themselves CRLF, so staging them would produce a mixed-EOL blob rather than a clean one. The clean fix is a whole-file LF renormalization, which is Prime's action.
