## 2. The one genuine gap your request adds: real per-work-item token capture

Everything above is *dispatch-scoped* and, for tokens, *estimated*. Your specific ask — "token consumption
of each **work item** action" — needs two things GT-KB does **not** have today:

**(a) Real token counts at the harness boundary.** GT-KB never reads the model API's usage numbers. Each
harness CLI already emits them (codex, claude, `agy`, ollama, openrouter all surface prompt/completion
tokens). The activation is: capture the harness's usage output at process exit and record actual
`input_tokens`/`output_tokens` instead of the character heuristic. The **naming standard** is OpenTelemetry
GenAI semantic conventions — `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`,
`gen_ai.request.model`, `gen_ai.system` (provider), and a derived `llm.cost.usd`. The cost formula is
`cost_usd = (input_tokens × in_price + output_tokens × out_price) / 1e6`.

**(b) Attribution up the chain.** Today the budget ledger is keyed to `dispatch_id` only. To get
*per-work-item* cost you need the join `LLM-call → dispatch_id → bridge_thread(slug) → work_item(WI)`.
Good news: the `stage_attempt_telemetry` table **already has the columns** (`token_count INTEGER`,
`cost REAL` — `db.py:665-698`) and is written by `typed_artifact_flow.py:450`; it is simply keyed to TAFE
`flow_instance_id`/`stage_instance_id` rather than to a bridge slug or WI. The OTel **parent-span roll-up**
pattern is the clean model: child span = one LLM call, parent span = the bridge thread / work item, and the
parent aggregates child `llm.cost.usd` + tokens. That parent total *is* your "per-work-item token consumption."

## 3. Isolating the harness effect (your Ollama-vs-OpenRouter idea)

Your intuition is strongly validated by the external state of the art. The **Artificial Analysis Coding
Agent Index** does exactly this: it **holds the model constant** (Claude Opus 4.7) and **varies the harness**
(Cursor / Claude Code / OpenCode), measuring Pass@1 (quality), cost/task, tokens/task (input/cached/output),
and wall-clock/task. The published magnitude is striking: the *same model* in two harnesses can differ **32×
in cost at near-identical quality**, and LangChain moved a coding agent **30th→5th on Terminal-Bench 2.0
without changing the model**. Harness choice is a first-class variable, not noise.

GT-KB is unusually well-positioned to run this cleanly because the **same bridge task** can be dispatched to
two harnesses. The schema already carries `harness_id` + `provider` + `model`, so a controlled experiment is:

- Pin **D (ollama)** and **F (openrouter)** to the **same underlying cloud model** (both are cloud-routing
  harnesses today — D pins `deepseek-v4-pro-cloud`, F is unpinned). Dispatch an identical fixture/bridge task
  to both. Diff the four dimensions. The delta is the **harness effect**, model held constant.
- Caveat: truly-*local* models are "unpriced" in the budget config, so for those the cost dimension collapses
  to $0 and the harness effect shows in **tokens + latency + quality** instead of dollars. A cloud-vs-cloud
  pairing (D vs F on one cloud model) keeps all four dimensions live.

`benchmark_dispatch_envelope.py` already models a `BenchmarkDispatchEnvelope` + `run_tier` ("smoke", …) and
a `benchmark_mode` distinct from durable role assignment — i.e. the harness for an *experiment* run without
touching production dispatch. That is the seam a live A/B runner plugs into.

## 4. Implementation options (activation slices, cheapest first)

These are framed as advancing the **existing** program, not net-new build. Each is a candidate bridge slice.

**Option A — "Earn the scorecard from data you already log" (cheap; ~1 slice).**
A new benchmark module (fits the existing `BenchmarkResult` framework, `scripts/benchmarks/common.py:26-48`,
CLI `python -m scripts.benchmarks.cli`) that joins `dispatch-failures.jsonl` + `dispatch-diagnostic-post.jsonl`
+ bridge verdict outcomes into a **per-harness scorecard**: reliability (failure-rate by class),
responsiveness (median/p90 verdict latency), and quality-outcome (GO/NO-GO/VERIFIED rates, revision cycles).
**No new token capture.** Immediate value: turns the static `dispatch_quality`/`availability` guesses into
observed numbers, and turns today's `worker_timeout` WARN into a data point. This is essentially **WI-4969**.

**Option B — "Real token capture + WI/bridge attribution" (medium; your core ask).**
Capture each harness CLI's usage output at process exit; record actual `input_tokens`/`output_tokens`/`cost`
using OTel GenAI names; attribute `dispatch_id → bridge slug → WI`; reuse the `stage_attempt_telemetry`
columns. Upgrades the budget ledger from *estimated* to *actual*. This is the slice your request specifically
adds emphasis to and is the prerequisite for a trustworthy **cost** dimension.

**Option C — "Live quality adjudication" (harder; = WI-4791, Phase 4).**
Wire the `adjudication_score` that is currently `"unavailable"`: consensus capture calibrated by
seeded-flaw fixtures (the exact WI-4791 title). This is how "fit-for-purpose" becomes measurable beyond the
deterministic gate-pass score. Already backlogged; the hardest dimension; do it last.

**Option D — "Same-model / different-harness A/B runner" (rides on B).**
A `benchmark_mode` runner that dispatches one fixture task to two harnesses pinned to the same model and diffs
the four dimensions. Directly answers "compare the effect of the harness itself." Depends on B for the cost
dimension to be real.

**Option E — "OTel-native, dashboard-ready" (north-star; optional).**
Emit true OTel GenAI spans so the data flows into the time-series dashboard KPI that
`GOV-SESSION-SELF-INITIALIZATION-001` already *requires* (it mandates "tokens consumed at session start" as a
dashboard KPI) and that `DCL-SESSION-STARTUP-TOKEN-BUDGET-001` anticipates but which is currently unimplemented.
Standards-aligned; the most work; pursue only if/when the live dashboard is prioritized.

Recommended sequence: **A → B → D → (C, E as their WIs mature).** A and B together give you three of four
dimensions on *real* data and the same-model experiment; C/E are the long tail.

## 5. Risks / honest caveats

- **Quality is the hard dimension.** Deterministic gate-pass ≠ fit-for-purpose. Real quality needs
  ground-truth or rubric adjudication (WI-4791). Treat GO/NO-GO/VERIFIED rates + revision cycles as an
  *interim proxy*, clearly labelled as such.
- **Cost confounds.** Cache pricing (OTel notes cached-input vs fresh-input), local "unpriced" models, and
  provider markup all distort raw $ comparisons. Compare tokens *and* dollars, and hold the model constant.
- **Task-difficulty confound.** Cross-task cost/quality comparisons are noisy; the *same-task A/B* (Option D)
  is what actually isolates the harness. Cross-harness aggregates need normalization or fixed fixtures.
- **Don't let measurement mutate ranking silently.** The scaffold's `SAFETY_INVARIANT_IDS`
  (`harness_quality_manifest.py:62-71`) already forbid the benchmark from changing dispatcher eligibility.
  Keep earned scores *advisory* until you explicitly decide to close the loop.
