Owner Decision - WI-4987 dispatch failure-timer fix design (per-harness, generous-first)

DECISION (owner directive 2026-07-03): The immediate fix for WI-4987 is to set
PER-HARNESS worker timers, starting with GENEROUS allowances so that no
harness+model+config combination is falsely worker_timeout'd. As typical
per-harness/model behavior is observed, dial the timers in to improve efficiency
(iterative tightening, not a one-shot tuning).

CONTEXT: Harness+model+config combinations process work items at very different
rates - Qwen/Kimi ~1-2 min; Opus 4.8 Max 10-20 min normal; deepseek / gemini
vary. The current lifetime is per-ROLE (LO 1800s / PB 5400s over a 600s
run_with_status.py default), not per-harness, and slow-model workers (e.g.
harness B, claude-opus-4-8 --effort max) are killed at the ~600s default,
producing false worker_timeout (exit 124), spurious WARN dispatch health, and
dead-worker stale claims that block the reliable interactive loop.

DESIGN / AUTHORIZATION: Codex-A (Prime Builder) may implement WI-4987 via the
bridge protocol under PROJECT-GTKB-OPS-DISPATCHER-MODERNIZATION with this design:
- Per-harness worker-lifetime timers (env-tunable per harness id), replacing the
  single per-role value as the effective cap.
- Generous initial allowances per harness (err long; zero false timeouts is the
  bar for the first cut), e.g. fast local/cloud models modest, Opus 4.8 Max 20+
  min, others generous pending observation.
- Also fix the root symptom that the intended per-role LO lifetime (WI-4845,
  1800s) was not reaching the launched worker (B died at the 600s default) -
  verify daemon freshness / launch-path so the configured per-harness value
  actually applies.
- Keep the WI-4828 storm-watchdog + per-role concurrency caps as the runaway
  guards; a generous lifetime must not re-open the dispatch storm.
- Iterate: capture observed per-harness/model completion times and tighten the
  timers later for efficiency.

Loyal Opposition (this session and successors) verifies the implementation and
that no harness is falsely worker_timeout'd under normal completion times.
